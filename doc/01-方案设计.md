# Clard 完整代理管理工具 — 方案设计

> 版本：v0.1（设计稿） · 目标平台：Linux · 界面：TUI（ratatui） · 状态：待评审
> 参考实现：clash-verge-rev（已研读其 `config/profiles`、`core/service`、`core/sysopt`、`feat/tun`、`crates/clash-verge-logging`、`enhance/*`）

## 1. 目标与范围

把 clard 从「对接外部 mihomo 后端的 TUI 查看器」升级为「完整、独立运行的代理管理工具」：

- 内置管理 mihomo/clash 核心（下载 / 升级 / 启动 / 重启 / 停止）
- 多配置文件：本地文件、订阅 URL 导入、定时更新、一键切换
- 系统代理（gsettings）与 TUN 模式（Linux）
- 完善的日志系统（应用日志 + 核心日志，分级、轮转、TUI 内查看）
- 保留 TUI 交互，沿用 M/V/C 分层思想，但允许对现有代码破坏性重构

**非目标（本期）**：Windows/macOS 适配；GUI；JS 脚本增强（boa_engine）暂列可选；多用户/远程控制。

## 2. 总体架构

采用「核心库 + TUI 前端」的 workspace 结构，业务逻辑与 UI 彻底解耦：

```
┌────────────────────────────────────────────────────────┐
│ clard-bin (main.rs, clap CLI)                          │
│   启动顺序：解析 CLI → 初始化日志 → 装配 App → 跑事件循环 │
└───────────────────────────┬────────────────────────────┘
                            │ 使用
┌───────────────────────────▼────────────────────────────┐
│ clard-tui (ratatui + crossterm)                        │
│   app 状态机 / canvas 绘制 / event 输入 / widgets        │
│   只通过 ClardEvent 与 core 交互，不直接碰系统资源        │
└───────────────────────────┬────────────────────────────┘
                            │ 调用（trait 边界）
┌───────────────────────────▼────────────────────────────┐
│ clard-core（纯领域逻辑，无 TUI 依赖，可单测）              │
│  ├ profile    配置文件 CRUD / URL 导入 / 定时更新调度      │
│  ├ config_gen 配置生成链（merge/override + tun/dns 注入） │
│  ├ sidecar    核心进程生命周期 + 就绪探测                  │
│  ├ runner     运行方式：sidecar(子进程) vs systemd(特权)   │
│  ├ sysproxy   gsettings 系统代理 开关/旁路/恢复            │
│  ├ tun        TUN 能力检测与使能                          │
│  ├ mihomo     external-controller HTTP/WS 客户端          │
│  ├ logging    日志管道（文件轮转 + 内存环形缓冲）           │
│  └ store      持久化（XDG 目录、profiles.yaml、clard.toml）│
└────────────────────────────────────────────────────────┘
```

原则：

- **core 不依赖 ratatui**，所有副作用（系统代理、核心进程、网络）都在 core 内通过 `Result` 暴露。
- TUI 只做「展示 + 派发命令 + 消费事件」，业务状态收敛在 core 与 TUI 的 app 状态机之间明确分工。
- 沿用现有事件循环模型（见 §9），这是 clard 里已被验证的部分，直接保留。

## 3. 模块划分与职责

| 模块 | 职责 | 关键输入/输出 | 破坏性影响 |
|---|---|---|---|
| `profile` | 配置文件的索引与内容管理 | `profiles.yaml` 索引、`profiles/*.yaml` 内容 | 取代现有 `ipc` 之外的零散逻辑 |
| `config_gen` | 由「基础配置 + 覆盖片段」生成运行时配置 | 输入：当前 profile + merge/rules/proxies/groups + tun/dns 设置；输出：临时 `config.yaml` | 新增 |
| `sidecar` | 核心进程句柄、启停、健康探测、崩溃检测 | `Child`、`external-controller` 就绪轮询 | 取代 `default_backend()` 的探测逻辑 |
| `runner` | 抽象运行方式：子进程 / systemd 服务 | `trait CoreRunner` | 新增 |
| `sysproxy` | gsettings 读写、旁路列表、退出恢复 | `sysproxy-rs` | 新增 |
| `tun` | 能力探测（是否已 setcap/服务是否可用）、使能/禁用 | `enable_tun_mode` | 新增 |
| `mihomo` | 对 `external-controller` 的 REST + WebSocket | 现有 `src/ipc` 迁移而来 | 保留并瘦身 |
| `logging` | 文件日志（分级/轮转）+ 内存环形缓冲 | `tracing` | 新增 |
| `store` | XDG 路径、配置读写、迁移 | `clard.toml`、`profiles.yaml` | 新增 |

## 4. 核心进程管理（sidecar）

### 4.1 核心产物与目录

mihomo/clash 核心以独立二进制打包，存放在数据目录：

```
$XDG_DATA_HOME/clard/
  core/
    mihomo              # 核心可执行文件
    core.db             # fake-ip / 缓存数据库
  profiles/             # 各配置片段文件（uid.yaml / uid.js）
  runtime/
    config.yaml         # 生成的运行时配置
    secret              # external-controller secret
$XDG_CONFIG_HOME/clard/
  clard.toml            # 应用设置
  profiles.yaml         # 配置索引（元数据）
$XDG_STATE_HOME/clard/
  logs/                 # 日志目录（app / core）
```

核心的下载/升级走 GitHub Release 或用户指定 URL，校验 checksum，原子替换（下载到临时文件再 rename）。

### 4.2 运行方式抽象

TUN 需要 `CAP_NET_ADMIN`，普通用户进程没有。因此抽象 `CoreRunner`，按需选择：

| 运行方式 | 提权方式 | TUN | 复杂度 | 适用 |
|---|---|---|---|---|
| `SidecarRunner` | 无（子进程） | ✗ | 低 | 默认、仅 HTTP/SOCKS + 系统代理 |
| `SystemdRunner` | systemd unit（root） | ✓ | 中 | TUN 模式，开机自启，崩溃拉起 |
| `SetcapRunner`（可选） | 一次性 `setcap cap_net_admin=+ep` 核心二进制 | ✓ | 低 | TUN 模式，免装服务，但核心以用户身份运行 |

首期实现 `SidecarRunner` + `SystemdRunner`，`SetcapRunner` 作为轻量替代方案放在二期。

### 4.3 生命周期状态机

```
NotRunning ──start──▶ Starting ──ready──▶ Running ──stop──▶ Stopping ──▶ NotRunning
                         │                    ▲
                         └──failed/超时──▶ Failed ──retry──┘
```

- **就绪探测**：启动后轮询 `GET /version`（带 secret），带超时与退避；未就绪时其余功能降级。
- **崩溃检测**：监听子进程退出 / systemd 状态变化，推送 `CoreStatusChanged` 事件，TUI 提示并允许重试。
- **配置重载**：优先 `PUT /configs?force=true`（热重载）；涉及 tun/dns/ports 变更时整进程重启。
- **串行化**：所有 start/stop/restart 经同一把 `tokio::sync::Mutex`，避免并发启停竞态。

## 5. 配置文件管理（Profiles）

### 5.1 配置类型与索引

沿用 clash-verge 的 `PrfItem` 概念，简化如下：

```yaml
# profiles.yaml
current: "R_xxx"
items:
  - uid: "R_xxx"
    type: remote            # remote | local | merge
    name: "订阅A"
    file: "R_xxx.yaml"
    url: "https://.../sub"
    desc: ""
    updated: 1730000000
    extra: { upload: 0, download: 0, total: 0, expire: 0 }
    option:
      update_interval: 1440      # 分钟
      user_agent: ""
      with_proxy: false
      allow_auto_update: true
    selected:                    # 节点选择持久化
      - { name: "Proxy", now: "节点B" }
```

- `type`：`remote`（订阅）、`local`（本地文件）、`merge`（覆盖片段）。首期不支持 script/rules/proxies/groups 四类独立片段，直接以 merge 片段承载覆盖需求。
- 每个 profile 一个 `uid`，文件落盘到 `profiles/uid.yaml`。

### 5.2 URL 导入

1. 输入订阅 URL（可选：名称、更新间隔、自定义 UA、是否走代理下载）。
2. `reqwest` 下载，遵循 `profile-update-interval`（小时）、`Content-Disposition`（文件名）、`subscription-userinfo`（流量/到期）响应头。
3. 校验 YAML 合法且包含 `proxies` 或 `proxy-providers`，否则拒绝导入并报原因。
4. 生成 uid、写文件、追加索引、保存。若订阅 URL 重复，提示覆盖或跳过。

### 5.3 定时更新

- 每个 profile 独立调度，用 `tokio_util::time::DelayQueue` 维护到期队列（参考 clash-verge `core/timer.rs`）。
- 到期后异步拉取，成功则更新 `updated` 时间戳与文件；失败记录日志并保留旧文件，**下次按完整间隔重试，不因失败导致 0 延迟热循环**。
- 启动时检查「上次更新 + 间隔 < 当前时间」的过期项，立即补一次。
- 更新开始/完成/失败都发事件，TUI 在 Profiles 页显示「更新中… / 上次更新 / 下次更新」。
- 更新竞态：同一 uid 同一时刻只允许一个在途更新（`running` 标记，参考参考实现的 `TaskState`）。

### 5.4 切换配置

切换 = 五步事务，任一步失败回滚到旧配置：

1. **生成运行时配置**（§6）写入临时文件。
2. **重载/重启核心**（§4.3）。
3. **恢复节点选择**（`selected` 中记录的分组→节点，按可用性校验后下发）。
4. **刷新系统代理/TUN**（端口未变则只刷新，变了则重写）。
5. **更新 `current` 索引并持久化**。

切换期间 TUI 进入「切换中」状态，屏蔽并发切换。

## 6. 配置生成链（config_gen）

运行时配置不直接等于某个订阅文件，而是「基础配置 + 覆盖」的合成结果：

```
基础 profile (remote/local)
   └─▶ merge 覆盖（全局 merge + 当前 profile 的 merge，深合并 Mapping）
        └─▶ 注入应用托管字段（app-managed，覆盖用户值）：
             - external-controller: 127.0.0.1:{mixed_port}
             - secret
             - mixed-port / redir-port / socks-port
             - allow-lan / bind-address
             - mode（可选覆盖）
             - log-level
             - tun: { enable, stack: system|gvisor, dns-hijack, auto-route }
             - dns: { enable, enhanced-mode: fake-ip, fake-ip-range, ... }
        └─▶ 序列化为 runtime/config.yaml
```

- 用户字段与托管字段分层：托管字段（ports/tun/dns/external-controller）永远由应用注入，用户改动不生效，避免端口冲突与安全暴露。
- 深合并语义：Map 递归合并，Scalar 后者覆盖前者，List 整体替换。
- 首期不做 JS 脚本增强；预留 `config_gen` 的 `Chain` 接口以便后续插入脚本步骤。

## 7. 系统代理（sysproxy，Linux）

- 后端：`sysproxy-rs`（clash-verge 同款），Linux 走 gsettings（`org.gnome.system.proxy`）。
- 能力：
  - 全局代理开/关（http/https/socks 指向 `127.0.0.1:mixed_port`）
  - 旁路列表（默认本地网段 + 用户自定义）
  - 可选 PAC（首期不做）
  - **退出时恢复**：正常退出与 panic 都恢复系统代理为「关闭」，防止残留导致断网
- 守护（可选）：定时重写系统代理（默认关闭，设置页开关），应对其他程序改动。

## 8. TUN 模式（Linux）

- **能力判定**：`TunState { Capable, NotCapable(reason) }`。SystemdRunner 已安装且可用 → Capable；否则 NotCapable。
- **使能**：写入 `tun.enable=true`（含 `dns-hijack`、`auto-route`、`fake-ip`），用 SystemdRunner 启动核心。
- **降级**：用户开启 TUN 但服务不可用时，明确提示「需安装 systemd 服务 / 或 setcap」，并允许自动关闭 TUN 回退 sidecar（参考 `feat/tun.rs` 的 reconcile 逻辑）。
- **DNS**：TUN 下强制 fake-ip 与劫持，避免 DNS 泄漏；退出时清理。

## 9. 数据流与并发模型

沿用并扩展 clard 现有事件循环（已验证可用）：

```
输入源(crossterm) ─┐
mihomo WS 推送 ────┤──▶ mpsc::unbounded_channel<ClardEvent> ──▶ 主循环 tokio::select!
核心状态变化 ──────┤                                             │
定时器/更新结果 ────┘                                             ▼
                                             消费事件 → 改 app 状态 → painter.draw
```

**硬性约束**：

- 异步任务（网络、核心探测、更新）**只 send 事件，绝不直接改 app 状态**。
- 主循环单线程串行消费，天然避免数据竞争；核心内的共享状态用 `ArcSwap` / `DashMap` 表达。
- 事件枚举扩展：

```rust
enum ClardEvent {
    // 输入
    Resize, KeyInput(..), MouseInput(..), PasteEvent(..), Terminal,
    // mihomo 数据
    UpdateGroups(..), UpdateConnections(..), UpdateTraffic(..), NodeTested(..),
    NetTestNodesReady(..), NetTestError(..),
    // 核心/配置
    CoreStatusChanged(CoreStatus), ProfileUpdated { uid, result },
    ProfileUpdateStarted(uid), ProfileUpdateFinished(uid),
    // 日志
    LogLine(LogRecord),
    Error(String),
}
```

## 10. 日志系统（logging）

双层日志（应用 + 核心），三处出口（文件、内存环形缓冲、TUI 页）：

- **应用日志**：`tracing` + `tracing-subscriber`，按级别过滤（默认 info，`RUST_LOG` 可覆盖），文件按大小轮转（默认 1MB × 保留 5 个）。
- **核心日志**：核心的 stdout/stderr 或核心自身日志文件，逐行写入独立 sidecar 文件（不落应用文件），同时进内存环形缓冲（默认 1000 行）供 TUI 实时展示。
- **内存环形缓冲**：`VecDeque` + `RwLock`，`append/get/clear`，TUI 日志页读取。
- **TUI 日志页**：合并/分栏查看 app 与 core 日志，级别过滤、跟随尾部、清屏。
- **日志级别**：`error > warn > info > debug > trace`，运行时可通过设置页调整（`reload` 过滤层）。
- **panic hook**：恢复终端 + flush 日志 + 打印背trace，避免 TUI 下 panic 留下烂终端。

## 12. 错误处理

- `clard-core` 统一 `anyhow::Result`（内部）＋ 边界处转 `ClardError`（用户可读）。
- TUI 层用 `app.message` 展示最近错误/通知，重要错误进日志页。
- 可恢复错误（订阅更新失败、延迟测试失败）不中断主流程；致命错误（核心无法启动、配置非法）在状态区醒目提示并给出操作建议。

## 13. 里程碑（建议顺序）

| 阶段 | 内容 | 可验收 |
|---|---|---|
| M1 | workspace 拆分 + `logging` + `store` + `sidecar`(SidecarRunner) + `config_gen`(最小链) | 能内置启动核心、生成配置、日志落盘 |
| M2 | `profile` CRUD + URL 导入 + 定时更新 + 切换 | 导入订阅、定时更新、一键切换可用 |
| M3 | `mihomo` 客户端迁移 + TUI 重构（Profiles/Proxies/Connections 三页） | TUI 内完成核心操作 |
| M4 | `sysproxy` 系统代理 + 退出恢复 | 系统代理开关、恢复正常 |
| M5 | 日志页 + 设置页（级别/轮转/端口） | 日志可视、设置生效 |
| M6 | `tun` + SystemdRunner（TUN 模式） | TUN 可开启、无泄漏、降级提示正确 |
